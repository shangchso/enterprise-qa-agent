# 02 方案设计

## 1. 总体架构

```
enterprise-qa-agent/
├── run.py                # CLI 入口
├── src/
│   ├── agent.py          # ReAct 检索与冲突处理循环
│   ├── llm.py            # MockLLM / RealLLM
│   ├── data_store.py     # 数据加载、片段展平、对话历史
│   └── tools/            # 文档检索、片段读取
├── data/                 # 合成文档与问题
├── tests/                # 单元测试
├── examples/traces/      # 场景 Trace
└── docs/                 # 文档
```

## 2. ReAct 调用流程

```
模型选择动作 → 执行工具 → 观察结果 → 更新状态 → 模型决定下一步或结束
```

典型路径：

1. `document_search` 检索候选片段。
2. 逐个 `fragment_reader` 读取原文。
3. 模型根据候选数量与冲突情况选择回答 / 冲突说明 / 资料缺口。
4. 达到 `max_steps` 强制结束并返回 `incomplete`。

## 3. 冲突检测与处理（高分点）

`data/documents.json` 中：

- D01（2025-01-10）：报销期限 **30 天**。
- D02（2025-06-01）：报销期限 **15 天**。
- 两者未给适用范围与优先级。

检测规则：同一 `topic` 下出现不同 `answer_value` 即判定冲突。冲突时
Agent 输出 `conflict_items`（含两个文档的原文引用）并请求确认适用制度，
**不凭空回答 15 天**。只检索到 D01 且无冲突时，才依据 D01 回答。

## 4. 检索改进：同义改写与追问

- 每个片段配置 `keywords`（含同义词，如"出差住、住一晚"对应差旅），
  支持改写后的相似问题命中。
- 追问时先按问题文本匹配；文本未命中才用上下文话题兜底，避免把同话题
  无关片段误纳入答案。

## 5. 技术取舍

- **Python 原生实现**：仅用标准库，不引入框架，便于评审检索与冲突逻辑。
- **默认 MockLLM**：离线确定性复现；Mock 只验证流程，不代表真实模型效果。
- **预留 RealLLM**：OpenAI 兼容接口，配置 `LLM_API_KEY` 启用，`urllib` 实现。
